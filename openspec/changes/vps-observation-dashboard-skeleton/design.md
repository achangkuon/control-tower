# Design: VPS Observation Dashboard Skeleton

## Decision summary

Build an isolated `dashboard/` service with Bun's built-in HTTP server, standard Web APIs, and dependency-free HTML, CSS, and browser JavaScript. The Bun process owns authentication and protected rendering; Caddy owns public TLS and reverse proxying; systemd owns process supervision. No dashboard module imports or calls Control Tower runtime code.

The protected flow is deliberately narrow:

```text
browser
  -> Caddy (public HTTPS, proxy only)
  -> Bun auth guard
  -> mock source
  -> five-field view-model allowlist
  -> escaped HTML renderer
  -> authenticated browser
```

The auth guard runs before the mock source. Public login, asset, and health responses contain no fixture values. The renderer receives only the allowlisted view model, so source properties outside the five permitted logical fields cannot become visible by accident.

## Scope and architectural boundary

This change creates a presentation service, not a Control Tower adapter.

| Area | Design boundary |
|---|---|
| Dashboard responsibility | Authenticate one maintainer and render representative, project-grouped mock observations. |
| Displayed record data | Exactly project name, agent name, state, task title, and branch name. |
| Runtime authority | None. The service cannot command, approve, mutate, or write operational state. |
| Control Tower dependency | None. The service does not import `core.mjs`, `mcp.mjs`, bot/Telegram code, Tower runtime files, or their databases. |
| Projection integration | Deferred. No real payload, transport, persistence, freshness, continuation, or P4-P6 semantics are defined here. |
| Persistence | None for dashboard records. Mock fixtures are read-only application files; sessions are signed cookies rather than stored records. |
| Deployment | A standalone Bun process deployed independently from the Control Tower service. |

The in-process source return shape is a presentation seam only. It is not a network message, storage schema, synchronization contract, or commitment about a future laptop-to-VPS projection.

## Minimal web stack

### Selected stack

- **Runtime and server:** Bun 1.3.x with `Bun.serve` and standard `Request`/`Response` APIs.
- **Server modules:** JavaScript ESM (`.mjs`) to match the repository.
- **Authentication primitives:** `Bun.password.verify` for an Argon2id password hash and `node:crypto` for random values, HMAC signing, and timing-safe comparison.
- **UI:** semantic HTML, one CSS file, and a small dependency-free browser module.
- **Tests:** `bun:test`, using unit and HTTP integration tests.
- **Build:** none. The deployable files run directly under Bun.
- **VPS boundary:** systemd supervises the loopback-bound Bun process; Caddy terminates HTTPS and reverse-proxies to it.

This stack adds no framework, bundler, package manager metadata, client hydration layer, or runtime database. It is compatible with the repository's Bun/ESM conventions and keeps the independently deployed dashboard self-contained.

### Request surface

| Route | Authentication | Purpose | Protected source access |
|---|---:|---|---:|
| `GET /login` | No | Render the username/password form. | Never |
| `POST /auth/login` | No | Validate credentials and issue a session cookie or render the generic auth-failure state. | Never |
| `GET /` | Yes | Render the application shell with the explicit loading state. | Never |
| `GET /dashboard/content` | Yes | Resolve the selected source and render populated or empty content. | Yes, after the guard |
| `GET /assets/dashboard.js` | No | Load behavior for the authenticated shell; contains no fixture data. | Never |
| `GET /assets/styles.css` | No | Load presentation styles; contains no fixture data. | Never |
| `GET /healthz` | No | Return process availability only, without dashboard or credential data. | Never |

All other routes return `404`; unsupported methods return `405`. The only POST is the authentication exchange. It changes browser authentication state but has no operational authority and cannot reach Control Tower state.

## Authentication and non-disclosure boundary

### Credential configuration

Credentials are supplied outside the release directory through a root-owned environment file, never committed to the repository:

- `DASHBOARD_AUTH_USERNAME`
- `DASHBOARD_AUTH_PASSWORD_HASH` — Argon2id hash generated by the included operator script
- `DASHBOARD_AUTH_REVISION` — an operator-controlled revision string
- `DASHBOARD_SESSION_SECRET` — at least 32 random bytes, encoded for environment transport
- `DASHBOARD_AUTH_DISABLED` — when true, all login attempts and existing sessions fail closed

The process refuses to start if required authentication configuration is missing, malformed, or insecure. It never accepts a plaintext configured password.

A login attempt uses one generic failure message and does not reveal whether the username or password was wrong. Username comparison uses a fixed-size digest and timing-safe comparison. Password verification still runs against a valid dummy hash when the username does not match, avoiding a materially different failure path. Credentials and submitted passwords are never logged.

### Session design

After successful login, the server issues a short-lived, HMAC-signed cookie containing only a format version, authentication revision, expiry, and random nonce. It contains no mock data and no operational authority.

The cookie is:

- `Secure`
- `HttpOnly`
- `SameSite=Strict`
- scoped to `Path=/`
- bounded to an eight-hour maximum lifetime

Every protected request verifies the HMAC, expiry, current auth revision, and disabled flag before any source module is invoked. Invalid, expired, disabled, or prior-revision cookies are treated as unauthenticated.

### Rotation and revocation

Credential rotation is an operator action:

1. Generate a new Argon2id password hash and session secret.
2. Increment `DASHBOARD_AUTH_REVISION`.
3. Atomically replace the environment file.
4. Restart the systemd service.
5. Confirm the prior password and prior cookie fail, then confirm the new pair succeeds at the same URL.

Changing the password hash, revision, and signing secret invalidates both the old credentials and all old sessions. Setting `DASHBOARD_AUTH_DISABLED=true` and restarting revokes access without introducing a replacement credential. Neither operation changes the dashboard hostname or URL.

### Protected response ordering

The router classifies the route first, then applies the auth guard, and only then constructs the protected handler dependencies. In particular:

- unauthorized `GET /` redirects to `/login` without loading fixtures;
- unauthorized `GET /dashboard/content` returns a generic `401` without loading fixtures;
- invalid `POST /auth/login` renders only login interface copy;
- public JavaScript and CSS do not import, embed, or fetch mock fixtures;
- protected HTML and content responses use `Cache-Control: no-store` and `Vary: Cookie`;
- authentication and server errors never include stack traces, source values, or fixture values.

A source spy in integration tests will prove that all unauthenticated paths stop before source invocation. This ordering is the primary non-disclosure control; hiding content with CSS is explicitly forbidden.

## Source, view-model, and renderer architecture

### Data flow

```text
MockDashboardSource.load()
        |
        | presentation-only candidate records
        v
buildDashboardViewModel(sourceOutput)
        |
        | explicit allowlist + validation + project grouping
        v
DashboardView
        |
        | populated or empty presentation state
        v
renderDashboardContent(view)
        |
        | escaped semantic HTML
        v
authenticated response
```

The renderer never imports the mock source or fixture. The server composes the source, mapper, and renderer through constructor parameters so tests and a future source adapter can replace the source without changing rendering behavior.

### Five-field view contract

The canonical populated view has this logical structure:

```js
{
  kind: "populated",
  projects: [
    {
      projectName,
      agents: [
        { agentName, state, taskTitle, branchName }
      ]
    }
  ]
}
```

`kind`, `projects`, and `agents` describe presentation structure; they are not dashboard record fields. The five logical data fields are exactly:

1. `projectName`
2. `agentName`
3. `state`
4. `taskTitle`
5. `branchName`

The mapper constructs fresh objects by reading only those five named values. It does not spread source objects. Unexpected properties are ignored and cannot reach the renderer. Required values must be strings; invalid candidates fail closed rather than being coerced, fabricated, or partially rendered. An empty candidate list becomes `{ kind: "empty" }`.

Grouping uses `projectName` only. The project name appears once as the group heading; each child record renders agent name, state, task title, and branch name. The mapper and renderer do not define state enums, timestamps, ordering guarantees, identifiers, freshness, or lifecycle meaning.

The mock adapter may contain representative examples, but the seam is strictly in-process and presentation-only. A future source must translate its own undefined upstream representation into this five-field seam. Nothing in this design specifies how that source obtains, transports, stores, or refreshes data.

### Rendering safety

The server renderer escapes all five values before creating HTML. State remains an opaque display string and is rendered as readable text plus a decorative marker hidden from assistive technology. Color and glow supplement the text but never replace it.

The browser module fetches `/dashboard/content` with same-origin credentials and replaces the loading region with the server-rendered fragment. It contains no fixture constants and does not generate new record fields. Content Security Policy disallows inline scripts, third-party origins, objects, and framing.

## Presentation states

| State | Trigger | Presentation | Disclosure rule |
|---|---|---|---|
| Authentication failure | Invalid, revoked, disabled, or malformed authentication | Login form plus a generic failure message; focus returns to the error/form. | No source call and no protected values. |
| Loading | Authenticated application shell is visible while `/dashboard/content` resolves. | One compact skeleton region with `aria-busy="true"` and neutral loading copy. | No record value is fabricated. No transport, freshness, or runtime claim is shown. |
| Populated | The source returns one or more valid candidates. | Project sections containing stacked agent records. | Exactly the five allowed logical fields. |
| Empty | The source returns no candidates. | A concise empty-state heading and presentation-only guidance. | No record or operational metadata is invented; no transport, persistence, freshness, or lifecycle claim is shown. |

A source exception does not masquerade as an empty result. It fails closed with generic unavailable interface copy and no records; this is error containment, not a defined transport or runtime lifecycle state.

## Mobile-first UI and visual direction

The interface starts as a single-column project list at 320 CSS pixels. It remains a restrained list at wider widths rather than becoming a multi-panel command center.

### Information hierarchy

1. A small page heading identifies the observation dashboard.
2. Each project is a semantic section with `projectName` as its heading.
3. Each agent is a stacked record beneath the project heading.
4. Within a record, the readable order is agent name, state, task title, and branch name.

No project counts, timestamps, activity feeds, metrics, search, navigation rail, commands, quick actions, timelines, voice controls, provider status, or system monitoring panels are added.

### Responsive behavior

- The content column uses the full phone width with safe padding and a readable maximum width on larger screens.
- Records use vertical label/value rows; they do not rely on a desktop table.
- Long task and branch values wrap with `overflow-wrap: anywhere`.
- At 320 CSS pixels, all five permitted fields remain readable without horizontal scrolling; the page sets no fixed content width.
- Touch targets apply only to authentication controls; the dashboard itself has no action controls.
- A manual 320 CSS pixel verification complements CSS contract tests because no browser E2E runner is configured.

### Visual language

The supplied reference contributes only palette and surface treatment:

- near-black navy page background;
- slightly lighter navy project surfaces;
- cyan/teal borders and accents;
- restrained, localized glow around headings or state markers;
- high-contrast body text and muted labels;
- state text always present, with a non-color marker shape.

Glow is decorative and reduced under `prefers-reduced-motion`/accessibility preferences. The design does not reproduce the reference's desktop density or modules.

## Concrete module structure for apply

All implementation is additive and contained under `dashboard/` plus dashboard-specific tests:

```text
dashboard/
  server.mjs                         # Bun entry point; reads config and starts loopback server
  app.mjs                            # request routing and dependency composition
  auth.mjs                           # credential verification, signed cookie, auth guard
  view-model.mjs                     # exact five-field allowlist, validation, grouping
  render.mjs                         # login, shell, empty, and populated escaped HTML
  sources/
    mock-source.mjs                  # replaceable source implementation
    mock-fixtures.mjs                # representative server-only examples
  public/
    dashboard.js                     # authenticated content fetch and state replacement
    styles.css                       # mobile-first command-center treatment
  scripts/
    hash-password.mjs                # operator-only Argon2id hash generation
  deploy/
    control-tower-dashboard.service  # hardened systemd unit example
    Caddyfile.example                # HTTPS reverse proxy example
    dashboard.env.example            # names only; no usable secrets

test/dashboard/
  auth.test.mjs
  view-model.test.mjs
  render.test.mjs
  server.test.mjs
  architecture.test.mjs
```

No file under `dashboard/` imports a repository file outside that directory. Tests may inspect dashboard files but do not import or mutate Control Tower runtime state.

## Strict TDD strategy for apply

Apply follows **RED -> GREEN -> TRIANGULATE -> REFACTOR** for each behavior slice. A failing test is recorded before implementation; the smallest implementation makes it pass; a second case triangulates the boundary; refactoring happens only while the focused and full suites remain green.

### Test layers

| Layer | Intended evidence |
|---|---|
| Unit: authentication | Correct/dummy password verification paths, signed-cookie validation, expiry, disabled auth, revision mismatch, malformed inputs, and generic failure behavior. |
| Unit: view model | Project grouping, exact five-key projection, unexpected-property removal, invalid-value rejection, and explicit empty output. |
| Unit: renderer | HTML escaping, semantic project grouping, readable state text, exact permitted labels/values, and absence of prohibited metadata. |
| HTTP integration | Unauthenticated and invalid-auth responses contain no fixture values and never call the source; valid auth reaches shell/content; old cookies fail after rotation; empty and populated responses are distinct; unsupported routes/methods fail closed. |
| Architecture contract | Public assets contain no fixtures; renderer does not import fixtures; dashboard modules do not import `core.mjs`, `mcp.mjs`, bot/Telegram, Tower runtime, or autonomous-continuation artifacts; externally exposed operations have no operational write path. |
| Responsive contract | CSS has a mobile-first single-column baseline, wrapping rules, and no fixed desktop grid. Manual verification at 320 CSS pixels checks real readability and horizontal overflow. |

Tests inject credential configuration, clock/random functions, and a source spy. They use unique sentinel fixture values so non-disclosure assertions can search complete response bodies and public assets. Extra candidate properties include prohibited examples to prove the mapper drops them.

### Commands

Focused RED/GREEN cycles:

```bash
bun test test/dashboard/auth.test.mjs
bun test test/dashboard/view-model.test.mjs
bun test test/dashboard/render.test.mjs
bun test test/dashboard/server.test.mjs
bun test test/dashboard/architecture.test.mjs
```

Full regression command after every completed slice and before verification:

```bash
bun test
```

There is no build command, configured coverage threshold, or automated browser E2E layer. Apply must not invent one. Deployment smoke checks are separate from `bun test` and must use non-production credentials.

## VPS service and deployment shape

### Process and proxy boundary

- Caddy is the only public listener and owns HTTPS certificates, HTTP-to-HTTPS redirect, and reverse proxying.
- Bun binds to `127.0.0.1` on a configured unprivileged port; it is not reachable directly from the network.
- Authentication remains in Bun, not Caddy, so every protected app route shares the same testable guard and explicit failure UI.
- systemd runs Bun as a dedicated unprivileged user with `NoNewPrivileges`, `PrivateTmp`, `ProtectHome`, and a read-only filesystem policy. No Control Tower database, worktree, SSH credential, or operational socket is made available to that user.
- Logs go to journald and include request outcome categories only. They exclude submitted credentials, cookies, query values, mock records, and response bodies.

### Release layout

```text
/opt/control-tower-dashboard/releases/<release-id>/dashboard/
/opt/control-tower-dashboard/current -> releases/<release-id>/dashboard/
/etc/control-tower-dashboard/dashboard.env
```

A release copies only the self-contained `dashboard/` directory. The environment file is root-owned with restrictive permissions and stays outside release directories. The service starts with:

```text
/usr/bin/bun /opt/control-tower-dashboard/current/server.mjs
```

The proxy route and hostname remain stable across releases and credential rotation.

### Rollout and rollback

1. Copy a new immutable release directory.
2. Verify its files and configuration without exposing it publicly.
3. Atomically move the `current` symlink.
4. Restart the systemd unit.
5. Check `/healthz`, unauthenticated non-disclosure, and one authenticated populated/empty smoke path.

If verification fails, point `current` back to the previous release and restart. Because the dashboard has no record database, migration, queue, projection checkpoint, or write authority, rollback requires no data repair or Control Tower action. Credential revocation is independent: disable auth or rotate the external credential file, then restart.

## Security and privacy constraints

- HTTPS is mandatory at the public boundary; the Bun listener remains loopback-only.
- Protected handlers authenticate before source creation or invocation.
- Public responses and assets contain no mock record values.
- Credentials, hashes, session secrets, cookies, and submitted passwords are never logged or committed.
- Login requests have a small body limit, accept only the expected form fields, enforce same-origin form submission, and return a generic failure.
- Session cookies are signed, short-lived, secure, HTTP-only, same-site, revision-bound, and invalidated by rotation or disablement.
- Protected responses are non-cacheable and vary on the session cookie.
- HTML values are escaped; the browser script uses only same-origin responses. CSP restricts scripts/styles to self and denies objects, base changes, and framing.
- Security headers include `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy`, and frame denial through CSP.
- The service has no API token, repository write access, SSH key, Control Tower database access, command runner, mutation route, approval route, or operational socket.
- UI controls are limited to the authentication form. Authenticated dashboard content is observation-only.
- Error responses disclose neither source values nor implementation stack traces.

## Architecture decisions and rejected alternatives

### ADR-1: Use Bun and platform APIs without a web framework

**Decision:** Use `Bun.serve`, ESM, and vanilla browser assets.

**Rationale:** The repository already depends on Bun, the service is small, and a build pipeline or framework would add supply-chain and deployment surface without improving the required hierarchy.

**Rejected:** React/Vite, Next.js, and server frameworks. They add dependencies, generated assets, or routing/build conventions disproportionate to this skeleton.

### ADR-2: Keep authentication inside the Bun application

**Decision:** Use a form login, Argon2id hash verification, and revision-bound signed sessions.

**Rationale:** App-level guarding can be tested before source invocation, provides the explicit auth-failure state, and makes credential rotation invalidate existing sessions.

**Rejected:** Proxy-only HTTP Basic authentication. It couples behavior to proxy configuration, usually produces browser-owned prompts, and weakens application-level proof that every protected response stops before source access. Long-lived JWTs are also rejected because revocation is harder and unnecessary for one maintainer.

### ADR-3: Render protected content on the server behind a loading shell

**Decision:** Serve an authenticated shell first, then fetch an authenticated server-rendered content fragment.

**Rationale:** This provides a real loading state without bundling fixtures into public assets, keeps escaping centralized, and avoids a client framework or DOM test dependency.

**Rejected:** A public client-only application containing mock JSON, because it would disclose protected values before authentication. Embedding records directly in the initial shell is rejected because it removes the source-resolution loading boundary.

### ADR-4: Enforce the disclosure boundary in a dedicated view-model mapper

**Decision:** Construct fresh objects from an explicit five-field allowlist and render only that canonical view.

**Rationale:** Source extras cannot drift into the UI, fixtures remain replaceable, and exact-field tests have one authoritative seam.

**Rejected:** Passing source objects directly to templates or using object spread. Both make accidental disclosure likely and couple rendering to fixture shape.

### ADR-5: Deploy as a separate loopback service behind Caddy/systemd

**Decision:** Use a dedicated unprivileged systemd service and Caddy reverse proxy.

**Rationale:** This supplies stable HTTPS, process restart, credential rotation, and symlink rollback while keeping the dashboard isolated from Control Tower authority.

**Rejected:** Hosting inside `core.mjs`, `mcp.mjs`, the plugin, or another Tower process. That would cross the child boundary and create avoidable authority and failure coupling. A public Bun listener is rejected because it bypasses the TLS/proxy boundary.

### ADR-6: Preserve a single-column hierarchy at desktop widths

**Decision:** Scale spacing and maximum width, but retain project-grouped stacked records.

**Rationale:** The phone hierarchy is the product, while the reference image supplies only visual language.

**Rejected:** Responsive conversion into navigation rails, metric grids, timelines, feeds, or command panels. Those add prohibited fields/modules and recreate the reference's desktop density.

## Requirement traceability

| Requirement | Design mechanism | Primary test evidence |
|---|---|---|
| Authenticated browser access | Guard-before-source routing, Argon2id verification, revision-bound cookie | Auth unit tests and source-spy HTTP tests |
| Revocation/rotation without URL change | External env file, auth revision and signing-secret rotation, systemd restart | Prior-cookie/prior-password rejection integration test |
| Observation-only authority | Isolated service user, read-only process, route/method allowlist, no Tower imports | Architecture and route enumeration tests |
| Exact five-field disclosure | Fresh-object view-model allowlist and renderer contract | Extra-property and prohibited-sentinel tests |
| Mobile project hierarchy | Semantic project sections and stacked records from 320 CSS pixels | Renderer/CSS contract tests plus manual viewport check |
| State without color alone | Visible state text and decorative marker | Renderer accessibility assertion |
| Explicit states | Login failure, loading shell, populated content, empty view | Renderer and HTTP integration tests |
| Replaceable source seam | Injected `source -> view-model -> renderer` composition | Fake replacement source integration test |
| VPS deployability | Self-contained Bun directory, systemd unit, Caddy proxy, release symlink | Deployment smoke procedure |
| Deferred real projection | Presentation-only source seam and no transport/storage/runtime modules | Architecture import and documentation checks |

## Known risks

| Risk | Mitigation |
|---|---|
| A route reaches fixtures before authentication. | Central guard ordering plus source spies and sentinel searches across every unauthenticated response. |
| Mock structure is mistaken for a future projection protocol. | Keep it server-only, name it presentation-only, and define no transport, persistence, freshness, or lifecycle behavior. |
| Extra source properties become visible. | Allowlist into fresh view objects; never spread source objects; test prohibited sentinel properties. |
| Credential rotation leaves old sessions valid. | Bind cookies to both auth revision and rotated signing secret; verify old cookies after restart. |
| Proxy misconfiguration exposes Bun directly. | Bind only to loopback and document Caddy as the sole public listener. |
| Visual direction becomes dense or color-dependent. | One-column mobile hierarchy, explicit state text, no extra modules, and a 320-pixel manual check. |
| Lack of browser E2E automation misses a responsive defect. | Keep CSS simple, add contract tests, and require a manual phone-width smoke check during apply/verify. |

## Apply constraints

The apply phase must remain additive to `dashboard/` and `test/dashboard/`. It must not edit or import bot/Telegram, `core.mjs`, `mcp.mjs`, Tower runtime, autonomous-continuation artifacts, P4-P6 artifacts, or real projection integration. It must not add any displayed record field, operational action, real projection payload, transport, persistence, freshness, or continuation semantics.
