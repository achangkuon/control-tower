# Audit G — Registries that force cross-Zona edits

> **Scope.** Read-only sweep for every file with the shape found in Audit E: a file living in one
> Zona that enumerates paths owned by another, so adding an asset of the kind it governs forces an
> edit from outside its own Zona. §4's threshold makes such a file a Cimiento; `radar check` cannot
> see it, because `owners()` resolves declared path rules and each of these files has exactly one
> owner.
> **Method.** Mechanical. Ownership reimplemented from `partition.go` `owners()` against the
> partition in the Fase B candidate; 213 tracked code files scanned for **collection literals**
> (object keys, array members) naming another tracked file with a different owner; results
> classified by hand.
> **Date.** 2026-09-04. **Bases.** `control-tower/Main@850d5bc` · partition from
> `openspec/changes/migrate-control-tower-plan-zones/migration/candidate/plan.yaml` (in flight).

---

## Verdict

**Three files carry the defect, all three in `instalacion`, and one of them is ten times larger
than the case that started this.** Documentation was excluded on the canon's own rule — a plan
citing `hosts/foo.mjs` is not edited when that file changes — which drops the raw 166 hits to 12
code files, of which 8 merely reference Cimientos (legitimate: Cimientos exist to be referenced).

**The repository already solved this problem once, by generation.** That precedent decides which
remedy each case gets.

---

## 1. The three real cases

| File | Lives in | Enumerates | Hand-edited? |
|---|---|---|---|
| `test/install/runtime-payload.test.mjs` | `instalacion` | 55 paths from **6** owners | yes — `CANONICAL_RUNTIME_PAYLOAD` |
| `test/install/tower-role-assets.test.mjs` | `instalacion` | 6 paths from **2** owners | yes — `ASSET_CONTRACTS` |
| `test/install/payload-closure.test.mjs` | `instalacion` | 6 paths from **2** owners | yes — expected entrypoints |

### 1a. `runtime-payload.test.mjs` — the large one

`CANONICAL_RUNTIME_PAYLOAD` (line 9) is a hand-maintained golden copy of the installable payload:
34 paths from `contratos`, 13 from `hosts`, 5 Cimientos, 2 from `asientos`, 1 each from `jornada`
and `enrolamiento`.

Adding one schema in `contratos` propagates: the generator adds it to the payload, and the golden
must then be updated **by hand, inside `instalacion`**. Six Zonas can each force an edit to one
file owned by a seventh.

### 1b. `tower-role-assets.test.mjs` — the case from Audit E

`ASSET_CONTRACTS` (lines 12-107, 96 of the file's 295 lines) declares three profiles owned by Zona
`asientos` and three skills that are Cimientos, from inside `instalacion`. Three-way, not two-way.

### 1c. `payload-closure.test.mjs`

The expected entrypoint set names `hosts/launch-worker-cli.mjs` and `hosts/seat-cli.mjs`. Same
shape, smallest blast radius.

## 2. The precedent: generation already fixed the worst instance

`install/runtime-payload.mjs` looks like the biggest offender — 56 foreign paths from 6 owners —
and is **not a defect at all**:

```js
// <generated:runtime-payload>
// Regenerate exactly with: BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 bun scripts/payload-closure.mjs --write
export const RUNTIME_PAYLOAD_FILES = [
```

Nobody hand-edits it. The list is **derived from the import graph** by `scripts/payload-closure.mjs`
— which is itself already declared a Cimiento. There is no cross-Zona edit because there is no
edit at all: adding a contract regenerates the list.

This is the first remedy, and where it applies it is strictly better than the second: a derived
list cannot drift and needs no reservation.

---

## 3. Which remedy each case gets

The deciding question is **whether the list is derivable**.

| Case | Derivable? | Remedy |
|---|---|---|
| `install/runtime-payload.mjs` | yes, from the import graph | **already generated** — nothing to do |
| `tower-role-assets.test.mjs` | **no** — carries human-authored contract | **extract + declare Cimiento** |
| `runtime-payload.test.mjs` | no, *deliberately* | **extract + declare Cimiento** |
| `payload-closure.test.mjs` | no, *deliberately* | **extract + declare Cimiento** |

`ASSET_CONTRACTS` is not derivable: it holds expected frontmatter values and three sets of regex
`markers` pinning exact sentences. No tool computes those from the tree; a human decides what a
skill must promise.

The two golden lists are not derivable **on purpose**. A golden generated by the code it checks
proves nothing — the whole point is that a human confirms the generator's output. Generating them
would delete the test's value, so extraction is the only sound remedy.

### The extraction, concretely

Data moves to its own module; logic stays. The file need not leave its directory:
`partition.go:81-83` lets an exact-file Cimiento **carve** a file out of a broad Zona route, and
that behaviour is covered by `TestCimientoExactoRecortaUnaRutaAmpliaDeZona`.

```
test/install/tower-role-assets.contract.mjs   → Cimiento   (the 96 data lines)
test/install/tower-role-assets.test.mjs       → instalacion (the 187 logic lines)
```

`instalacion` keeps its test. It releases only the data that was never its own.

## 4. What is not a defect

Eight of the twelve candidates only **reference** Cimientos — `core.mjs`, `mcp.mjs`, `bin/torre`,
`install.sh`, `README.md`: `agent-workflows/test/{cli,measure}.test.mjs`,
`test/install/lifecycle.test.mjs`, `install/lifecycle.mjs`,
`agent-workflows/tools/radar/check_test.go`, `test/contracts/session-plan-snapshot.test.mjs`,
`test/main-store.test.mjs`, and `scripts/payload-closure.mjs` (already a Cimiento).

Referencing a Cimiento is what Cimientos are for. Only a file that must be **edited** when another
Zona's asset changes carries the defect.

Documentation is excluded by the canon's own table — *«Documentation — that is not code»*. The
`autoridad` Zona (`openspec/plans/`) produced the largest raw counts (`plan-4/STATUS.md`, 55;
`decision-register.md`, 52) and none of them qualifies: a plan naming a file is a citation, and
nothing forces the plan to change when that file does.

---

## 5. The generalisable rule

> **If a file mixes data several Zonas need with logic only one Zona owns, split it. The data is a
> Cimiento; the logic stays in its Zona. If the data is derivable, generate it instead and the
> problem disappears entirely.**

Generation is the stronger remedy and is preferred whenever the list can be computed. Extraction
is for lists a human must author.

`radar check` cannot enforce this rule, and no change to it would: ownership is declared over
paths, while the threshold is about who edits. Detection stays a review question — this audit is
the method, and it is re-runnable.

---

## 6. Method, for repeatability

Ownership was reimplemented from `partition.go` `owners()`, including the exact-Cimiento carve-out.
Only **collection literals** were counted — object keys and array members — because a path inside
an import or a sentence is a reference, not a declaration. Files needed 2+ foreign-owned paths to
appear. Documentation extensions and the `autoridad`/`archivo` Zonas were excluded per §4.

Counts: 512 tracked text files → 166 with any foreign path (too noisy, mostly documentation) →
213 code files scanned → 12 with an enumerated foreign collection → **3 genuine**.
