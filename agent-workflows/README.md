# Agent Workflows

Version-controlled source of truth for the user-owned Chanks skill family:
product Session coordination, plan authority and closure. Gentle AI owns technical
decomposition, implementation, checks, continuity and native SDD phase surfaces;
this package never replaces, edits or regenerates its managed assets.

The original Control Tower candidate flow is frozen byte-for-byte under
`product/tower/generic/`; it is product history, not active builder policy. The
active builder does not require roles, seats, dispatch, tokens, queues or an
external coordination API.

## Install by owner

**Control Tower is the single product installer.** Its reviewed V1 roster is
exported by `product/tower/v1/runtime-config.mjs`, from the release bundle. Tower
owns on each machine:

- V1 skills in `~/.agents/skills/` and their Claude links in `~/.claude/skills/`;
- the central `_shared/plan-naming-convention.md` and `~/.local/bin/radar`;
- Claude hooks `chanks-etapa.sh` and `torre-firma.sh`, including settings registration;
- Pi `~/.pi/agent/extensions/chanks-notices.ts`;
- the `control-tower:pointer` block in the four runtime instruction files.

The complete workflow lives in each adopted project's `AGENTS.md` (S196), not in
another global workflow block. Install/update these assets through the Tower's
product lifecycle, not through the maintainer's personal installer.

**`tools/install.py` only writes personal configuration.** The active non-V1
skills are `chanks-0-agente-soporte` and the maintainer's `torre-release` (from
[`skills-personales/`](skills-personales/README.md)). Both are installed centrally
and linked from Claude; neither ships in the Tower bundle or counts as a Tower
skill. The installer also manages four personal blocks:

| Template | Marker family |
|---|---|
| `templates/explain-to-maintainer.md` | `chanks:explain-to-maintainer` |
| `templates/doc-guard-rule.md` | `chanks:doc-guard-rule` |
| `templates/agent-propagation-map.md` | `chanks:agent-propagation-map` |
| `templates/main-freshness.md` | `chanks:main-freshness` |

Each block carries the same visible provenance comment: **Generated by Chanks
(personal configuration) — not part of Control Tower**. Opening and closing
markers delimit the only bytes that normal personal updates replace.

Gentle AI is an independent product with its own installation/update authority.
These skills do not ship with it; `author: gentleman-programming` frontmatter is
a historical template default, not provenance. Never copy Gentle AI skills or
managed `_shared` files into this repository.

### Migrate old personal configuration once

Source tests do **not** authorize writing the maintainer's real HOME. Obtain
separate authorization, then run from the repository root:

```bash
# Read-only by default: review every listed file/block and the skill handoff.
python3 agent-workflows/tools/install.py --migrate-to-tower

# Only after reviewing the dry-run and receiving explicit authorization:
python3 agent-workflows/tools/install.py --migrate-to-tower --apply
```

The migration preflights all four instruction files before writing anything:

| Runtime | Instruction file |
|---|---|
| Claude Code | `~/.claude/CLAUDE.md` |
| Codex | `~/.codex/AGENTS.md` |
| OpenCode | `~/.config/opencode/AGENTS.md` |
| Pi | `~/.pi/agent/APPEND_SYSTEM.md` |

It replaces existing `AGENT-PROPAGATION-MAP:MANUAL`, `doc-guard-rule` and
`EXPLAIN-TO-MAINTAINER:MANUAL` blocks with their personal Chanks templates. Legacy
openings may carry the exact existing manual annotation. It removes the
superseded `SESSION-SKILL-ARCHITECTURE:MANUAL` and `PLAN-NAMING:GLOBAL` blocks:
Tower's pointer plus project-local workflow replace their global role. It does
not install a pointer itself, invent missing blocks, or delete handed-off skills.
`STOP_MANAGING` reports precisely the 23 previously managed V1 skills, with their
files retained; the product-only `control-tower` skill was never in that roster.

Before the first instruction edit, **every affected file is backed up**, with its
relative path, bytes and mode, under
`~/.claude/.skill-backups/tower-migration/<UTC-stamp>-<unique>/`. Preserve these
backups. A second migration reports `NO_CHANGES` and creates no new backup.
Malformed, duplicated, overlapping, inline or nested owned markers, mixed
old/new aliases and symlinked destinations are refused before any write.

Unmarked bytes, `gentle-ai:*` and `control-tower:*` blocks are preserved exactly.
The **review-lifecycle-policy** block is managed by
`~/.claude/.skill-backups/manual-blocks.py`; it is out of scope and never migrated.
Do not restore an old manual snapshot over the new instruction files. Review
snapshot drift with its own owner before separately authorizing any refresh.

### Normal personal installation

After migration, authorize personal updates separately:

```bash
python3 agent-workflows/tools/install.py --dry-run
python3 agent-workflows/tools/install.py
python3 agent-workflows/tools/install.py --check
```

Normal installation leaves all legacy blocks untouched and prints a one-line
hint to run `--migrate-to-tower`. This remains compatible with `setup.sh`, which
still seeds legacy routing. The setup menu is a historical convenience wrapper,
not the authoritative Tower V1 deployment path. It no longer grants the personal
installer ownership of any Tower destinations.

Existing `chanks:*` blocks are replaced in place. Codex receives the personal
explanation and doc-guard blocks when absent, unless their legacy aliases are
still present. The propagation block remains replace-if-present. The freshness
block is appended when absent in all four runtimes, so every agent checks the
default branch at session start. No normal run
injects legacy routing or plan-naming into the four Tower-covered runtimes.
`--pi-notices-only` now refuses without writes: deploy notices through Tower.

Skills outside the current write roster remain untouched, including existing
V1 directories and Claude links. Personal skill copies in OpenCode/Codex are
archived reversibly as before; Claude real copies of the personal skill are
archived before linking. No per-runtime `_shared` overlay is written anymore.
Carril, the `main-al-dia` freshness launcher and the personal Pi npm host-peer
wrapper/settings and overlay rebuild tools retain their existing behavior; they
are not Tower-owned signature assets.

Absent runtimes are skipped. A present runtime with a missing instruction file
still fails closed. `--home PATH` isolates CLI destinations; tests also set HOME
to temporary directories. Restart affected runtime sessions after separately
authorized installation and verify instruction loading in fresh conversations.
File presence and fixture tests alone are not that verification.

Actual writes use a separate personal destination roster. Hermes is not covered
by Tower's four-runtime installer: its existing
`tools/prepare-personal-config.py` migration and legacy helper contract remain

The six non-V1 sources live in [`skills-diferidas/`](skills-diferidas/README.md),
grouped by version. `chanks-0-agente-soporte` lives under `skills-diferidas/v2/`
but remains installed as a personal skill, never as a Tower V1 bundle member.
Its installed links remain runtime-relative; its repository links follow the new layout.

`chanks-0-comunicacion-agentes` is not deferred: it is listed in `V1_PENDING_SKILLS`
until the Tower V1 package adds it, so neither Tower nor this installer writes it.
It covers what the user asks for by hand —message, observe or stop another agent,
open a pane— and cites the native `herdr` skill for commands. Automatic Session
dispatch stays in `chanks-3-despacho-herdr` (V3).

Every existing deferred-skill retirement remains unchanged: installed copies are
archived under `.retired-skills/`, never reinstalled. The retired Pi write-lock
shim `chanks-controls.ts` still moves to `.pi/agent/.retired-controls/`, outside
Pi discovery. Tower-owned `torre-firma.sh` is no longer a retirement candidate.

Obsolete files inside personal skills retire only on an explicit historical
path/SHA-256 match in `RETIRED_SKILL_FILES`. Modified, missing or unlisted files
remain intact; backups go under `.retired-skills/files/<stamp>-<unique>/`.
Historical tombstones inside Tower-owned skills are retained in the registry for
compatibility but never applied by this installer. Run without concurrent writers;
preflight/rechecks are not a filesystem lock or a transactional rollback system.

## Native Sessions

Native product coordination is `Zona → Sesión`. A Session declares Zona, identity,
priority/dependencies, exact authorized files, Cimientos/resources, authority, and
an `encargo` with exactly `pedido_contexto`, `resultado_comportamiento`,
`restricciones_decisiones` and `referencias`. ODD is the default technical path.
Its document and Engram record are continuity evidence, not another product plan.

SDD is available only after explicit human `solicitud_sdd`; Gentle AI's native
preflight/authority/archive controls apply. Complexity does not select it.
Historical legacy routes remain readable as evidence and are not retrofitted.
Native resume reconciles Session identity with its technical record, code and
checks; legacy resume retains first-pending-Módulo behavior.

## Radiografía

`radiografia/` generates a self-contained HTML product report from each project's
`radiografia.json` and `.githooks/pre-push`. It never blocks a push. See
`radiografia/README.md`; current adopters include control-tower, proyecto-beta,
Proyecto-Alpha and Proyecto-Gamma.

## Validation

Never run fixture verification against the real HOME:

```bash
cd agent-workflows
HOME=$(mktemp -d) PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -q
cd ..
HOME=$(mktemp -d) bun test agent-workflows
```

Do not edit `sdd-*`, Gentle AI's `_shared` files, `gentle-orchestrator`,
`opencode.json`, or managed instruction blocks.
